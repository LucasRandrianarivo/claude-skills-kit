# /a11y — Accessibility Audit & Fix

## Usage
```
/a11y                        — audit the routes/components changed on this branch
/a11y /checkout              — audit one route
/a11y src/components/Modal   — audit one component and every usage of it
/a11y --report-only          — audit without fixing
/a11y --level AAA            — raise the bar above the AA default
```

## Overview
Accessibility is not a lint rule. Automated tooling catches roughly a third of WCAG failures — the rest are keyboard traps, focus order, meaningless labels, and states only announced visually. This skill runs the automated pass **and** the manual passes that find the other two thirds, then fixes what it finds and re-verifies.

Target: **WCAG 2.2 level AA** unless `--level AAA`.

---

## Phase 1: Scope

1. Parse `$ARGUMENTS`. With no argument, scope to what changed: `git diff --name-only $(git merge-base origin/HEAD HEAD)` filtered to component/page/template files, then map each to the route(s) that render it.
2. Detect the toolchain: `@axe-core/playwright`, `axe-core`, `jest-axe`, `cypress-axe`, `eslint-plugin-jsx-a11y`, `@storybook/addon-a11y` — use what the project already has before adding anything.
3. Detect the component library (antd, MUI, Chakra, shadcn/Radix, Bootstrap, headless). Library primitives usually ship correct semantics; **the bugs are in how they're composed and in hand-rolled widgets**. Prioritize custom widgets.
4. Ensure the app runs; note the dev URL.

## Phase 2: Automated pass

Run axe against every in-scope route, at 1440px and 375px, in both themes if the app has a dark mode.

If the project has Playwright:
```
npx playwright test --grep @a11y            # if a11y specs exist
```
Otherwise write a throwaway script under the project's e2e folder that loads each route and runs `new AxeBuilder({ page }).analyze()`, and delete it after the run unless the user wants it kept.

Record every violation as `impact / rule / selector / route`. Automated findings are the floor, not the report.

## Phase 3: Keyboard pass (manual, mandatory)

For each interactive surface, drive it with the keyboard only — `page.keyboard.press` in Playwright, no mouse events:

| Check | Failure looks like |
|---|---|
| Tab reaches every control | A `div` with `onClick` and no `tabindex`/role — unreachable |
| Tab order matches visual order | `order`/`flex-direction: row-reverse`/absolute positioning desynced from DOM order |
| Focus is always visible | `outline: none` with no replacement ring; a ring invisible against its background |
| No keyboard trap | Focus enters a widget and cannot leave (WCAG 2.1.2) |
| Modal/drawer focus | Focus moves in on open, is trapped inside while open, returns to the trigger on close |
| Escape closes overlays | Dialog, popover, combobox, drawer |
| Enter/Space activate | `Space` on a `role="button"`, `Enter` on a link; both on a custom control |
| Arrow keys where expected | Menu, tabs, listbox, radio group, tree (WAI-ARIA authoring practices) |
| Skip link | First tab stop skips repeated navigation |
| Dragging has an alternative | WCAG 2.2 — 2.5.7 Dragging Movements |
| Target size ≥ 24×24 CSS px | WCAG 2.2 — 2.5.8 |
| Focus never obscured | Sticky headers/footers covering the focused element — WCAG 2.2 — 2.4.11 |

## Phase 4: Semantics & screen-reader pass

Read the DOM, not the design:

1. **Landmarks** — one `main`, `header`/`nav`/`footer` present, multiple same-type landmarks labelled.
2. **Headings** — one `h1` per page, no skipped levels, headings describe sections (not styled `div`s).
3. **Names** — every control has an accessible name (visible text > `aria-label` > `aria-labelledby`). Icon-only buttons: name says the action ("Delete invoice"), not the icon ("trash").
4. **Forms** — every input has a `<label for>` or wrapping label; placeholder is never the only label; errors are tied via `aria-describedby` and announced (`role="alert"` or a live region); required is conveyed programmatically, not by a red asterisk alone; autocomplete tokens on identity/payment fields (WCAG 2.2 — 3.3.7/3.3.8).
5. **State** — expanded/selected/checked/current/busy/invalid exposed via ARIA, not by class names alone.
6. **Live regions** — toasts, async results, validation summaries, and step changes announced once (`aria-live="polite"`, `assertive` only for errors).
7. **Images & media** — informative images have meaningful alt; decorative ones `alt=""`; charts/canvas have a text alternative or an accessible data table; video has captions.
8. **Language & title** — `<html lang>` correct; unique, descriptive `<title>` per route.
9. **Reduced motion** — animations respect `prefers-reduced-motion`.

## Phase 5: Contrast & zoom pass

- Text contrast ≥ 4.5:1 (≥ 3:1 for ≥24px or ≥19px bold); AAA raises this to 7:1 / 4.5:1.
- Non-text contrast ≥ 3:1 for control boundaries, focus rings, chart series, icons carrying meaning.
- Check disabled, hover, placeholder, and dark-mode variants — that is where contrast dies.
- Color is never the only carrier of meaning (status dots, required fields, diffs, chart series).
- Zoom to 200% and 400% (`page.setViewportSize({width: 320, height: 512})`): no horizontal scroll on content, nothing clipped, no fixed-height text container.
- `text-spacing` override does not break layout (WCAG 1.4.12).

## Phase 6: Report

```
## Accessibility Report — WCAG 2.2 <level>

Scope: <routes/components>   Automated: <n> violations   Manual: <n> findings

| # | Severity | WCAG | Where | Issue | Who it blocks | Fix |
|---|----------|------|-------|-------|---------------|-----|
| 1 | 🔴 | 2.1.1 A | Modal.tsx:44 | focus not trapped, Tab escapes behind the overlay | keyboard + screen-reader users | trap focus, restore to trigger on close |

Score: <blockers> blocker · <serious> serious · <minor> minor
```

**Severity ladder** — by consequence, never by rule count:
- 🔴 **Blocker** — a user of an assistive technology cannot complete the task at all (unreachable control, keyboard trap, unlabelled form, invisible focus).
- 🟡 **Serious** — the task is completable but degraded (bad order, unannounced errors, low contrast).
- 🔵 **Minor** — polish (redundant alt, heading level cosmetics, missing `lang` on a quoted phrase).

## Phase 7: Fix & verify

Unless `--report-only`:

1. Fix 🔴 then 🟡, one finding per edit.
2. Prefer **native semantics over ARIA**: a `<button>` beats `role="button"` plus three handlers. Only add ARIA when no element carries the semantics.
3. Never fix by hiding: `aria-hidden` on a focusable element, or `display:none` on a validation message, trades one failure for a worse one.
4. Do not "fix" contrast by drifting the brand palette — pick the accessible token that already exists in the design system, or flag it as a design decision for `/design-system`.
5. Re-run Phase 2 and re-drive the keyboard path for every fixed finding. Report before/after counts.
6. Add a regression guard where the project supports it (an axe assertion in an existing e2e spec, `jest-axe` on the component test, `eslint-plugin-jsx-a11y` rule enabled).

## Rules
- Cite `file:line` and the WCAG success criterion for every finding. No criterion, no finding.
- Never report an automated violation you have not confirmed in the DOM — axe reports on the rendered page, false positives happen with portals and virtual lists.
- Never disable an a11y lint rule to make a check pass; fix the markup or state the exception in the report with a reason.
- A component library bug is still a finding: report it, fix it at the composition level, and note the upstream issue.
- If nothing is wrong, say exactly `NO ACCESSIBILITY FINDINGS` and stop — do not manufacture minor issues.
