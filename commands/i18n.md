# /i18n — Internationalization & Localization

## Usage
```
/i18n --setup fr,en,es    — set up i18n for these locales
/i18n --audit             — find hardcoded strings and localization bugs
/i18n --extract           — extract new strings and sync the catalogs
/i18n --rtl               — add/verify right-to-left support
```

## Overview
Internationalization fails in ways that only appear in the second language: a sentence assembled from three fragments that can't be reordered, a German word that breaks the button, a date read as month/day in one country and day/month in another, a pluralization rule that doesn't exist in English. This skill sets up the structure that avoids those — and finds them where they already exist.

Uses the ecosystem's standard tooling (next-intl / react-i18next / i18next / vue-i18n / FormatJS / Django / Rails / Flutter `intl`) and the platform `Intl` APIs rather than hand-rolled formatting.

Field notes: `.claude/references/frontend.md` — mechanism, traps and the symptom→cause→fix tables for this domain.

## Phase 1: Decide the structure

| Decision | Guidance |
|---|---|
| **Locale in the URL** | `/fr/...` subpath (simplest, SEO-friendly) or subdomain. Never locale only in a cookie — it's unshareable and un-indexable |
| **Default & fallback** | One source locale; a missing key falls back visibly in dev (never silently to the key name in production) |
| **Detection** | `Accept-Language` on first visit → redirect to a locale URL → remember the choice; always allow an explicit switch |
| **Catalog format** | JSON/ICU per locale, split by feature; keys are semantic (`checkout.payment.declined`), never the English text |
| **Where translations come from** | The team, a TMS (Crowdin/Lokalise/Phrase), or a service — decide now, because it dictates the extraction workflow |

`hreflang` and `x-default` tags per locale, reciprocal across versions, and locale-specific sitemaps (`/seo`).

## Phase 2: Message rules — the part that decides whether translation is possible

1. **Never concatenate.** `"You have " + n + " items"` cannot be translated. One message with a parameter: `checkout.itemCount` = `{count, plural, one {# item} other {# items}}`.
2. **ICU plurals**, always — languages have up to six plural forms (Arabic, Polish, Russian); English's two are the exception, not the rule.
3. **Gender and select** where the language needs it (`{gender, select, ...}`), including for user names in sentences.
4. **No word order assumptions**: pass values as named parameters so translators can reorder freely.
5. **Context in the key or a comment**: `nav.home` vs `button.home` — the same English word is two different words elsewhere. Translators without context produce wrong translations.
6. **Rich text inside a message**, not split around markup: `{link}terms{/link}` handled by the library, so translators keep the sentence intact.
7. **Never translate at build time into the bundle for all locales** — load the active locale's catalog, split by route where the library supports it.

## Phase 3: Formatting — use `Intl`, never hand-rolled

- **Dates/times**: `Intl.DateTimeFormat` with the locale and an explicit time zone. Store UTC, render local. Never `toLocaleDateString()` with no locale, never a hand-built `DD/MM/YYYY` — the same string means two different days in the US and France.
- **Numbers**: `Intl.NumberFormat` — decimal separator, grouping, and negative-number placement all vary.
- **Currency**: format with the currency code, and never assume the symbol's position or that the locale determines the currency (a French user can pay in USD).
- **Relative time**: `Intl.RelativeTimeFormat` rather than "3 days ago" assembled by hand.
- **Sorting**: `Intl.Collator` — sorting names with `<` produces wrong order in most languages.
- **Lists**: `Intl.ListFormat` for "a, b and c" (the conjunction and comma rules differ).
- **Address, phone, name order**: don't assume first/last name order, postcode format, or that a state is required.

## Phase 4 (`--audit`): Find what's broken

| # | Check | Symptom |
|---|---|---|
| 1 | Hardcoded user-visible strings (grep JSX/templates for literal text, alt/aria/title attributes, error messages, emails, PDFs) | Untranslatable UI |
| 2 | Concatenated or interpolated sentences | Ungrammatical translations |
| 3 | Plural handled with a ternary on `n === 1` | Wrong in most languages |
| 4 | Dates/numbers formatted manually | Wrong day, wrong amount |
| 5 | Catalog drift: keys in code missing from catalogs, and unused keys left behind | Missing text in production |
| 6 | Fixed-width/height containers around text | German and Finnish overflow, Japanese under-fills |
| 7 | Text baked into images | Untranslatable, and invisible to search |
| 8 | `lang` attribute not switching with the locale | Screen readers use the wrong voice (`/a11y`) |
| 9 | Locale not propagated to the server (SSR renders one language, hydration another) | Hydration mismatch, flash of wrong language |
| 10 | Emails, invoices, push notifications and exports left in the source language | The half of the product nobody tests |

## Phase 5 (`--rtl`): Right-to-left

- Logical CSS properties everywhere: `margin-inline-start` not `margin-left`, `inset-inline`, `text-align: start`. Tailwind's `ps-*`/`pe-*` utilities.
- `dir="rtl"` on `<html>` per locale; mirror directional icons (arrows, chevrons, progress) but **not** logos, media controls, or numbers.
- Test with a real RTL locale (Arabic/Hebrew) at every breakpoint — mixed LTR content (code, URLs, brand names) inside RTL text is where layouts break.

## Phase 6: Workflow & verification

1. Extraction is a **command in the project** (`--extract`), run in CI: missing keys fail the build, unused keys are reported.
2. Pseudo-localization for testing: render `[Ṕŕöḋüçţ ńàṁé——]` — it catches hardcoded strings and tight containers before any translator is involved.
3. Verify by switching locale and walking the main flows: no untranslated string, no broken layout, correct dates/currency, correct `lang`, correct URL.
4. Translation is not a developer task: hand off catalogs with context, and never machine-translate user-facing copy into production without a human pass — say so plainly if asked to.

## Rules
- Never concatenate translatable text; one message, named parameters, ICU plurals.
- Never format a date, number, or currency by hand — `Intl` or the platform equivalent.
- Keys are semantic and carry context; the source text is never the key.
- A missing translation is visible in development and never silently shows a key in production.
- Don't ship machine translation as final user-facing copy; flag it as needing a human pass.
- Test with pseudo-locale and one real RTL locale before declaring support.
